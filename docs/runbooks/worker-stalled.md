# Runbook: воркер встал

**Алерты:** `NocturnWorkerDown`, `NocturnWorkerStalled`

## Impact

Незаметный для API инцидент: доступность и латентность остаются идеальными,
5xx нет. При этом останавливаются две вещи:

1. **Индексация заметок** — новые и изменённые заметки не появляются в
   семантическом поиске. Пользователь ищет свою вчерашнюю заметку и не находит.
2. **Очистка по retention** — не удаляются просроченные заметки из корзины,
   истёкшие refresh-токены и неподтверждённые аккаунты. Это медленно
   накапливающийся долг, а для токенов ещё и вопрос безопасности.

Именно поэтому существует метрика-heartbeat: без неё зависший воркер
обнаруживается только по жалобе пользователя.

## 1. Жив ли процесс

```bash
docker compose ps worker
docker compose logs --tail=100 worker
```

```promql
# Сколько секунд назад воркер закончил итерацию цикла
time() - nocturn_worker_last_loop_timestamp_seconds
```

Нормальное значение — до ~30 секунд (`EMBEDDING_QUEUE_INTERVAL_SECONDS`).
Больше 300 — цикл действительно завис, а не просто спит.

## 2. На чём завис

Цикл воркера состоит из четырёх шагов, и каждый ловит исключения отдельно,
логируя `step`. Найдите последний успешный:

```logql
{compose_service="worker"} | json | line_format "{{.ts}} {{.level}} {{.step}} {{.message}}"
```

| Что видно | Причина |
|---|---|
| `Worker step failed` с `step="embedding_queue"` | Провайдер эмбеддингов, см. [llm-provider-outage.md](llm-provider-outage.md) |
| Последняя строка `Processing embedding tasks`, дальше тишина | Зависание на сетевом вызове |
| Нет логов вообще | Процесс мёртв или не стартовал |
| `Cleanup error` | Долгая транзакция удаления, п.4 |

Зависание на сетевом вызове почти всегда означает запрос без таймаута.
Таймауты к провайдеру заданы явно (`LLM_CONNECT_TIMEOUT_SECONDS`,
`LLM_READ_TIMEOUT_SECONDS`) — если зависание всё же произошло, проверьте, что
эти переменные доехали в контейнер:

```bash
docker compose exec worker env | grep LLM_
```

## 3. Митигация

```bash
docker compose restart worker
```

Перезапуск безопасен: воркер обрабатывает `SIGTERM` и завершает текущую
итерацию, а задачи, брошенные в состоянии `processing`, через 15 минут
автоматически возвращаются в очередь reaper'ом (`requeue_stuck_tasks`).
Терять работу здесь нечем.

После перезапуска очередь начнёт разгребаться — следите за
[embedding-backlog.md](embedding-backlog.md), backlog может быть большим.

## 4. Долгая очистка

`run_cleanup` удаляет просроченные заметки по одной транзакцией, и при большом
накопленном хвосте (например, воркер стоял неделю) она может выполняться
минуты, блокируя цикл. Проверить:

```bash
docker compose exec postgres psql -U nocturn -d nocturn -c "
  SELECT count(*) FROM notes WHERE deleted_at < now() - interval '30 days';"
```

Если счёт идёт на десятки тысяч — удалите хвост вручную партиями, иначе
воркер будет уходить в очистку каждый цикл.

## Эскалация

Если воркер зависает повторно после перезапуска — отключите провайдера
эмбеддингов (очередь просто накопится, продукт останется работоспособным) и
разбирайтесь без давления инцидента. Заметки без эмбеддингов не теряются:
задачи остаются в `embedding_queue` и будут обработаны позже.
