# Runbook: деградация LLM-провайдера

**Алерты:** `NocturnLlmProviderErrors`, `NocturnLlmTimeToFirstTokenSlow`

## Impact

RouterAI — внешняя зависимость, которую мы не контролируем. Её отказ ломает
**половину продукта**, а не весь:

| Не работает | Работает |
|---|---|
| Чат с ассистентом | Создание, редактирование, удаление заметок |
| Предложения правок | Теги, корзина, восстановление |
| Индексация новых заметок | Поиск по уже проиндексированным |
| — | Логин, регистрация, админка |

Правильная коммуникация во время такого инцидента: «ИИ-функции временно
недоступны», а не «сервис лежит».

## 1. Подтвердить, что дело в провайдере

```promql
# Доля неуспешных вызовов
sum(rate(nocturn_llm_requests_total{outcome="error"}[10m]))
/ sum(rate(nocturn_llm_requests_total[10m]))

# По типам операций: чат и эмбеддинги могут отказывать по-разному
sum by (operation, outcome) (rate(nocturn_llm_requests_total[5m]))

# Время до первого токена
nocturn:llm_ttft:p95
```

```logql
{compose_service="backend"} | json | logger =~ ".*routerai.*" or level = "ERROR"
```

Прямая проверка снаружи приложения:

```bash
curl -sS -o /dev/null -w 'http=%{http_code} time=%{time_total}s\n' \
  -H "Authorization: Bearer ${ROUTERAI_API_KEY}" \
  https://routerai.ru/api/v1/models
```

## 2. Отличить их проблему от нашей

| Симптом | Скорее всего |
|---|---|
| `401` / `403` | Наша проблема: истёк или неверный ключ |
| `429` | Наша проблема: превышена квота |
| `5xx`, таймауты соединения | Их проблема |
| Растёт TTFT, ошибок нет | Их перегрузка, деградация без отказа |
| `model not found` | Наша проблема: модель переименована/снята |

Ключ и модели проверяются так:

```bash
docker compose exec backend env | grep ROUTERAI_ | sed 's/=.*KEY.*/=<hidden>/'
```

## 3. Митигация

**Таймауты уже стоят** и это главная защита: `LLM_CONNECT_TIMEOUT_SECONDS=5`,
`LLM_READ_TIMEOUT_SECONDS=120`, `LLM_MAX_RETRIES=2`. Без них зависший запрос к
провайдеру держал бы SSE-соединение и слот воркера до бесконечности —
деградация одного провайдера превращалась бы в отказ всего API.

Если провайдер отвечает очень медленно и это тянет за собой весь сервис:

```bash
# Ужать таймауты, чтобы быстрее отдавать пользователю ошибку вместо ожидания
docker compose up -d -e LLM_CONNECT_TIMEOUT_SECONDS=2 -e LLM_READ_TIMEOUT_SECONDS=30 backend
```

Если провайдер лежит полностью — отключите ИИ-функции, чтобы не копить
зависшие соединения и не жечь ретраи:

```bash
# Жёсткий, но честный вариант: снизить лимит на ИИ-эндпоинты почти до нуля
docker compose up -d -e RATE_AI_PER_MINUTE=1 backend
```

Очередь эмбеддингов останавливать не нужно: задачи накопятся в `pending` и
разгребутся сами, когда провайдер вернётся. Следите за
[embedding-backlog.md](embedding-backlog.md).

## 4. Ключ или квота

```bash
# Проверить, не упёрлись ли в лимит на их стороне
curl -sS -D- -o /dev/null -H "Authorization: Bearer ${ROUTERAI_API_KEY}" \
  https://routerai.ru/api/v1/models | grep -i 'ratelimit\|retry-after'
```

Истёкший ключ — самая частая «внешняя» авария, которая на самом деле наша.
Ротация ключа + перезапуск `backend` и `worker`.

## Эскалация

Не `page`. Причина в том, что чинить нечего: у нас нет рычага на чужой сервис.
Задача дежурного — подтвердить, что деградирована только ИИ-часть, и убедиться,
что она не утягивает за собой CRUD (проверить
`nocturn:availability:error_ratio5m` — он не должен расти).

Если провайдер недоступен дольше суток — это уже не инцидент, а решение о
резервном провайдере: клиент OpenAI-совместимый, смена `ROUTERAI_BASE_URL` и
`ROUTERAI_*_MODEL` технически достаточна.
