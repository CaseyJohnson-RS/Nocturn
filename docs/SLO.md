# Service Level Objectives

Определения ниже — источник истины. Правила в
[`observability/prometheus/rules/slo.yml`](../observability/prometheus/rules/slo.yml)
и панели в `Nocturn — SLO & Error Budget` выводятся ровно из них: если меняется
цель, сначала правится этот файл.

**Окно:** 30 дней, скользящее.
**Аудитория:** авторизованный пользователь веб-приложения.

---

## Почему выбраны именно эти SLI

У Nocturn два принципиально разных класса запросов, и мерить их одной метрикой
бессмысленно:

* **Синхронный CRUD** (заметки, теги, профиль) — пользователь ждёт ответа,
  измеряется временем ответа сервера.
* **Стриминг ИИ-ответа** — соединение живёт минуты, полное время ответа
  зависит от длины генерации и ничего не говорит о нашем качестве. Значимо
  только время до первого токена.
* **Асинхронная индексация** — заметка сохранена, но ещё не найдена
  семантическим поиском. Пользователь этого не видит в кодах ответа вообще,
  поэтому нужен отдельный SLI свежести.

Поэтому SLO четыре, а не один.

## SLO 1 — Доступность API

| | |
|---|---|
| **SLI** | Доля HTTP-запросов к `/api/*`, завершившихся **не** 5xx |
| **Цель** | **99.5%** за 30 дней |
| **Бюджет ошибок** | 0.5% ≈ 3 ч 39 мин полной недоступности в месяц |

```promql
sum(rate(nocturn_http_requests_total{path!="<unmatched>",status=~"5.."}[5m]))
/
sum(rate(nocturn_http_requests_total{path!="<unmatched>"}[5m]))
```

**Что исключено и почему:**

* `4xx` считаются успехом — это корректный ответ на некорректный запрос.
  Включая `429`: сработавший rate limit означает, что защита работает.
* `path="<unmatched>"` (запросы в несуществующие URL) исключены — сканер
  чужих админок не должен жечь наш бюджет.
* `/livez`, `/readyz`, `/metrics` не инструментируются вовсе: собственный
  мониторинг не должен влиять на измеряемую доступность.

**Почему 99.5%, а не 99.9%:** приложение живёт на одном инстансе без
резервирования, деплой рестартует процесс. Обещать три девятки при такой
архитектуре — обманывать себя; 99.5% оставляет бюджет на плановые деплои.

## SLO 2 — Латентность синхронного API

| | |
|---|---|
| **SLI** | Доля запросов вне `/api/ai/*`, обслуженных быстрее **250 мс** |
| **Цель** | **99%** за 30 дней |
| **Бюджет ошибок** | 1% медленных запросов |

```promql
1 - (
  sum(rate(nocturn_http_request_duration_seconds_bucket{le="0.25",path!~"/api/ai/.*"}[5m]))
  /
  sum(rate(nocturn_http_request_duration_seconds_count{path!~"/api/ai/.*"}[5m]))
)
```

**Два неочевидных решения:**

1. **Порог 250 мс совпадает с границей бакета гистограммы.** Любое другое
   значение Prometheus интерполирует — SLI превратился бы в оценку. Если нужен
   другой порог, сначала меняется список бакетов в `metrics.py`.
2. **Латентность измеряется до заголовков ответа, а не до последнего байта
   тела.** Иначе каждый SSE-стрим попадал бы в верхний бакет и уничтожал
   метрику. Реализовано в `ObservabilityMiddleware`.

## SLO 3 — Отзывчивость ИИ-ассистента

| | |
|---|---|
| **SLI** | Время от запроса до первого токена (TTFT), p95 |
| **Цель** | **p95 < 3 с** |

```promql
histogram_quantile(0.95, sum by (le) (rate(nocturn_llm_time_to_first_token_seconds_bucket[15m])))
```

Это то, что пользователь реально ощущает как «подвис». Полная длительность
генерации измеряется отдельно (`nocturn_llm_request_duration_seconds`), но
целью не является: длинный ответ — это не отказ.

**Зависимость от третьей стороны.** TTFT определяется в основном RouterAI.
Мы не контролируем их латентность, поэтому нарушение этого SLO — сигнал
«пора менять провайдера или включать деградацию», а не «чинить наш код».
Соответствующий алерт — `ticket`, не `page`.

---

## SLO 4 — Свежесть семантического поиска

| | |
|---|---|
| **SLI** | Возраст самой старой необработанной задачи эмбеддинга |
| **Цель** | **< 60 с** в нормальном режиме, алерт при **> 300 с** |

```promql
nocturn_embedding_queue_oldest_pending_seconds
```

Прокси-метрика вместо честной end-to-end: трассировать каждую заметку от
сохранения до появления в индексе дорого, а возраст головы очереди даёт
**верхнюю границу** отставания — если он ниже 60 с, то ни одна заметка не
отстаёт сильнее.

Это единственный SLI, который вообще не виден в HTTP-трафике: очередь может
встать намертво, а доступность и латентность останутся идеальными.

## Политика error budget

| Остаток бюджета | Что делаем |
|---|---|
| > 50% | Обычная разработка, деплои без ограничений |
| 25–50% | Деплои только с прогоном `make load-test` на staging |
| < 25% | Заморозка фич; в работе только надёжность |
| Исчерпан | Полная заморозка, обязательный постмортем |

## Алертинг

Алерты — **multi-window multi-burn-rate**, а не пороги на мгновенное значение.
Каждый требует одновременного превышения на длинном и коротком окне: длинное
окно отсекает шум, короткое гарантирует, что алерт погаснет вскоре после
устранения причины, а не будет висеть час.

| Burn rate | Окна | Бюджет сгорит за | Severity |
|---|---|---|---|
| 14.4x | 1 ч + 5 мин | ~2 дня | `page` |
| 6x | 6 ч + 30 мин | ~5 дней | `page` |
| 1x | 1 д + 2 ч | ровно 30 дней | `ticket` |

**При нулевом трафике алерты молчат** — деление на ноль даёт NaN. Это
осознанно: нет запросов — нет пострадавших. Полностью упавший сервис ловится
отдельным алертом `NocturnApiDown` по метрике `up`.
